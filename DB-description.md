# ТЗ: Схема базы данных

## 1. Таблица `profiles`

Профили пользователей системы.

| Поле   | Тип  | Ограничения            |
| ------ | ---- | ---------------------- |
| `id`   | uuid | PK, FK → auth.users.id |
| `name` | text | NOT NULL after profile-name backfill |
| `role` | enum `user_role` | NOT NULL         |

Допустимые роли:

- `director` — директор (постановщик);
- `employee` — исполнитель.

Термины в проекте: «директор» и «исполнитель».

Отдельная регистрация пользователей не требуется: используется Supabase Auth.

## 2. Таблица `objects`

Строительные объекты.

| Поле         | Тип         | Ограничения                |
| ------------ | ----------- | -------------------------- |
| `id`         | uuid        | PK                         |
| `owner_id`   | uuid        | FK → profiles.id, NOT NULL |
| `name`       | text        | NOT NULL                   |
| `address`    | text        | NOT NULL                   |
| `created_at` | timestamptz | NOT NULL, default now()    |

`owner_id` — постановщик, создавший объект.

Один объект может содержать множество задач.

## 3. Таблица `tasks`

Задачи, относящиеся к строительным объектам.

| Поле          | Тип         | Ограничения                |
| ------------- | ----------- | -------------------------- |
| `id`          | uuid        | PK                         |
| `object_id`   | uuid        | FK → objects.id, NOT NULL  |
| `employee_id` | uuid        | FK → profiles.id, nullable |
| `name`        | text        | NOT NULL                   |
| `description` | text        | nullable                   |
| `status`      | enum `task_status` | NOT NULL, default `new` |
| `created_at`  | timestamptz | NOT NULL, default now()    |
| `deleted_at`  | timestamptz | nullable (soft delete)     |

Допустимые статусы:

- `new` — новая;
- `in_progress` — в работе;
- `on_review` — на проверке;
- `accepted` — принята;
- `needs_work` — на доработке.

Особенности:

- `employee_id` может быть NULL, если исполнитель ещё не назначен.
- `status` содержит текущий статус и обновляется исключительно триггером при добавлении записи в историю.
- Прямое изменение `status` приложением запрещено.
- Задачу может создать, редактировать только директор, создавший родительский объект.
- `employee_id` должен указывать на профиль с ролью `employee` (проверка в триггере).
- Исполнителя можно назначить или сменить только в статусе `new` и только директором — владельцем объекта.
- Soft delete: задача помечается `deleted_at = now()`. Допускается только в статусе `new` и только директором — владельцем объекта. Удалённые задачи скрыты для всех ролей через RLS; история сохраняется.
- Прямые изменения `status`, `object_id` запрещены (`BEFORE UPDATE`-триггер и `REVOKE UPDATE` на колонку; RLS не ограничивает колонки). Исполнитель не имеет права `UPDATE` на `tasks`.
- Поля `updated_at` в схеме нет (убрано); время изменений статуса — в `task_status_history.created_at`.

## 4. Таблица `task_status_history`

История изменений статусов задач.

| Поле         | Тип         | Ограничения                |
| ------------ | ----------- | -------------------------- |
| `id`         | uuid        | PK                         |
| `task_id`    | uuid        | FK → tasks.id, NOT NULL    |
| `revision`   | integer     | NOT NULL                   |
| `status`     | enum `task_status` | NOT NULL            |
| `changed_by` | uuid        | FK → profiles.id, NOT NULL, `= auth.uid()` |
| `comment`    | text        | nullable                   |
| `created_at` | timestamptz | NOT NULL, default now()    |

Ограничения:

- `UNIQUE (task_id, revision)`.
- `comment` обязателен (непустой) при `status = 'needs_work'`.
- `revision` начинается с 1 и увеличивается на единицу при каждом изменении статуса конкретной задачи.
- История является append-only: существующие записи нельзя редактировать или удалять обычными операциями приложения.
- Начальное создание задачи сопровождается записью истории с `revision = 1` и `status = 'new'`.

Важно: поле `status` в истории — это состояние задачи на конкретной ревизии.

Предыдущий статус определяется по записи с `revision - 1`. Текущий статус — по последней ревизии.

## 5. Триггеры и бизнес-логика БД

### Триггер на `task_status_history`

После добавления новой записи истории (`AFTER INSERT`):

**`BEFORE INSERT`** (блокирует строку задачи `SELECT … FOR UPDATE`):

1. Проверяет, что `changed_by = auth.uid()`.
2. Проверяет, что задача не удалена (`deleted_at IS NULL`).
3. Проверяет, что ревизия — следующая для задачи (для первой записи: `revision = 1`, `status = new`).
4. Проверяет допустимость перехода статуса.
5. Проверяет права инициатора на этот переход (см. §7).
6. Требует непустой `comment` для `needs_work`.

**`AFTER INSERT`**: обновляет `tasks.status = NEW.status` (после успешных проверок).

Допустимые переходы:

| Из            | В             |
| ------------- | ------------- |
| `new`         | `in_progress` |
| `in_progress` | `on_review`   |
| `on_review`   | `accepted`    |
| `on_review`   | `needs_work`  |
| `needs_work`  | `in_progress` |

Создание задачи — исключение: первая запись истории имеет `revision = 1`, `status = new`.

### Защита от рассогласования

- Приложение не может самостоятельно менять `tasks.status`.
- Приложение не может редактировать или удалять историю.
- Обновление текущего статуса выполняется только триггером.
- Изменение статуса и добавление истории происходят в одной транзакции.
- Создание задачи — только через RPC `create_task` (`SECURITY DEFINER`): в одной транзакции вставляет задачу и запись истории `revision = 1`, `status = new`. Прямой `INSERT` в `tasks` клиентам запрещён.

## 6. Индексы

Предусмотреть следующие индексы:

| Таблица               | Индекс                     |
| --------------------- | -------------------------- |
| `objects`             | `owner_id`                                     |
| `tasks`               | `object_id` WHERE `deleted_at IS NULL`         |
| `tasks`               | `(employee_id, object_id)` WHERE `deleted_at IS NULL` |
| `tasks`               | `status` WHERE `deleted_at IS NULL`            |
| `task_status_history` | `(changed_by)`                                 |

Уникальный индекс `(task_id, revision)` обеспечивает быстрый поиск последней записи истории (отдельный индекс `revision DESC` не нужен).

## 7. Права доступа (RLS)

Включить RLS для всех пользовательских таблиц.

Директор (`director`):

- Просмотр всех объектов и всех неудалённых задач.
- Создание объектов; редактирование и удаление — только своих (`owner_id = auth.uid()`). Объект с задачами (в том числе с soft-deleted) удалить нельзя (`ON DELETE RESTRICT`).
- Создание и редактирование задач только своих объектов.
- Soft delete задачи — только своей и только в статусе `new`.
- Назначение/смена исполнителя — только у своей задачи и только в статусе `new`.
- Перевод `on_review` → `accepted` или `needs_work` для любой задачи любого объекта. Других переходов статуса у директора нет.
- Просмотр всей истории.

Исполнитель (`employee`):

- Просмотр только назначенных ему неудалённых задач.
- Просмотр объектов, в которых есть хотя бы одна назначенная ему задача.
- Перевод только своих (назначенных) задач: `new`/`needs_work` → `in_progress`, `in_progress` → `on_review`. Других значений нет.
- Просмотр истории назначенных ему задач. При переназначении или удалении задачи доступ теряется.
- Нет прав на создание, удаление и редактирование объектов и задач, кроме разрешённых переходов статуса.

Проверка роли и принадлежности задачи исполнителю должна выполняться на стороне БД, а не только в интерфейсе.

## 8. Важные замечания для реализации

Есть два момента, которые я специально рекомендую учесть агенту при генерации SQL.

1. Создание задачи. Создание задачи и первой записи истории должно происходить атомарно. Нельзя допустить появления задачи без начального статуса в истории.
2. Удаление задачи — soft delete через `deleted_at` (см. §3).

И ещё одно архитектурное уточнение: триггер должен быть не просто обработчиком `AFTER INSERT`. Проверка ревизии, авторизации инициатора и допустимости перехода должна происходить до фиксации изменения, с корректной блокировкой задачи. Само обновление `tasks.status` можно выполнять после успешной проверки.

Итоговая концепция: `task.status` — производное поле для удобства чтения; `task_status_history` — единственный источник истины о последовательности изменений.
